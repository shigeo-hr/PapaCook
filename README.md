# PapaCook(パパクック)

家にある食材から、AIが子供も大人も楽しめる献立を提案してくれる、休日パパのためのレシピアシスタントアプリ

---

## 1. サービス概要

**「わが家仕様」に育つ、休日パパのためのAI献立アシスタント**

PapaCook(パパクック)は、家にある食材を入力するだけで、AIが子供も大人も楽しめるレシピを提案してくれるアプリです。使うほど子供の反応を学習し、わが家仕様の提案に育っていきます。

**誰の、どんな課題を、どう解決するか**

料理経験が少ない30代〜40代のパパが、休日に子供の食事作りを任されたときの「アイデア不足」を、食材からのAI提案とフィードバック学習で解決する。

---

## 2. このアイデアはどこから生まれたか

休日、家族で過ごしていたときにふと妻から、平日仕事をしているのは自分だけではないこと、食事作りが当たり前に妻の役割になっていることへの違和感を伝えられた。

いつの間にか「食事作り=妻の仕事」という前提に自分自身が甘えていたことに気づかされ、ハッとさせられた。その通りだと思いながらも、いざ自分が作るとなると献立のアイデアが浮かばず、料理経験もそこまでないため簡単なものしか作れない自分にも気づいた。

家族は対等であるべきという考えに強く共感しており、休日くらいは自分がサクッと作れれば妻の負担を減らせるのではないかという思い、そして自分が作った料理で妻や子供達に「美味しい」と言ってもらえたら嬉しいという気持ちが、このアプリを作る原動力になっている。

---

## 3. 課題の整理(表面的になっていないか)

### 3-1. 表に見えている困りごと

休日のお昼前、妻に「今日どうする?」と聞かれた瞬間、何を作ればいいか思いつかず答えに詰まってしまう。そして、食材を見ながら一から考えるのが単純に面倒に感じてしまう。

### 3-2. 本当に解決したい課題は何か

- なぜ? → 献立が思いつかないと、結局いつも妻に頼ることになってしまうから
- なぜ? → 妻は平日も働いているのに、休日まで自分の代わりに献立を考えさせてしまうから
- なぜ? → 「休日くらいは自分が」という気持ちが行動に移せず、妻に余計な負担とストレスを与えてしまうから

**→ 本当に解決したい課題**

休日くらい妻の負担を減らしたいのに、献立が思いつかず結局妻に頼ってしまい、かえってストレスを与えてしまうこと

**年齢設定**
- 年齢:30代〜40代
- 理由:子育て世代で共働きが多い年代。自分自身も39歳で今年40歳になる

- 生活・状況:共働き家庭。自分は夜勤があるため平日の食事作りは妻が担当せざるを得ず、休日についても役割が決まっているわけではないが、結果的に妻に任せてしまっているのが現状(子供は小学生〜高校生を想定。例:11歳の娘と7歳の息子)
- 理由:妻の負担を減らしたいという思いがあるが、料理経験が少なく献立のアイデアが出ずに困っている

**環境設定**
- 環境:料理経験が少ない
- 理由:複雑なレシピだと挫折してしまうため、今ある食材からパッと提案してもらえる仕組みが必要

- 理由:まさに今、休日の子供の食事作りでアイデア不足に困っている当事者だから

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

**クラシル(Kurashiru)**
- **URL**:https://www.kurashiru.com/
- **主な機能**:
  - 冷蔵庫にある食材をカテゴリごとに選択し、レシピを提案
  - 「時短」「1人分」などのフィルター機能
- **不足している点**:
  - 子供の好き嫌いへの対応が弱い
  - フィードバック学習機能がない

**クックパッド**
- **URL**:https://cookpad.com/
- **主な機能**:
  - 日本最大級のレシピ投稿サイト
  - 食材からのレシピ検索が可能
- **不足している点**:
  - フィードバック学習機能がない
  - 子供向けの特化機能がない

**DELISH KITCHEN**
- **URL**:https://delishkitchen.tv/
- **主な機能**:
  - 動画レシピが豊富
  - 食材からのレシピ検索が可能
- **不足している点**:
  - 子供の好き嫌いに特化した機能がない
  - フィードバック学習機能がない

### 5-2. それでも自分が作りたい理由

クラシルは食材から献立を提案してくれるが、以下の点で自分の課題を完全には解決できないと感じた。

- **子供の好き嫌いまでは考慮されていない**
  わが家の場合、11歳の娘と7歳の息子それぞれ好き嫌いが違うため、汎用的な提案だけでは「結局子供が食べない」という問題は解決しない。

- **フィードバックを踏まえた学習機能がない**
  作った後の子供の反応(食べた/残した)を記録して、次の提案に活かすという仕組みが見当たらない。使うたびに自分の家庭に最適化されていく体験がない。

**だからこそ、自分の家庭に合った、使うほど賢くなるAI献立アシスタントを作りたい。**

### 5-3. 差別化を「体験価値」で表現する

このアプリは【料理経験が少ないパパ】の【休日に子供のご飯を任されて何を作ればいいか固まった瞬間】を一番助けるアプリ。

**私のアプリの差別化ポイント**:単なるレシピ検索・提案ではなく、子供の好き嫌いや調理後の反応を記録・学習することで、使うたびに「わが家仕様」に育っていくAI献立アシスタントであること。

## 7. このアプリで実現すること

このアプリが提供する価値は段階的に実現していく。MVPでは、まず「食材から子供も大人も楽しめるレシピをすぐに提案してもらえる」という基礎体験を実現し、献立を考える負担そのものを解消する。差別化の核である「使うほど『わが家仕様』に育つ」体験は、調理後フィードバック機能を実装する本リリース段階で検証する。

### MVPで作る機能(優先順位順)

1. **食材入力機能**
   家にある食材を選択・入力できる機能
   (画面イメージ:食材選択画面、よく使う食材のワンタップ選択)

2. **AIレシピ提案機能**
   入力した食材から、子供向け・時短などの条件を反映したレシピを提案
   (画面イメージ:レシピ提案画面、条件選択フィルター)

3. **子供プロフィール登録機能**
   子供の好き嫌いやアレルギー情報を登録し、提案に反映
   (画面イメージ:プロフィール登録画面、好き嫌い・アレルギー入力フォーム)

**MVPで検証する価値**:献立が思いつかず手が止まる時間をなくし、休日でもすぐに「子供のご飯係」として動けるようになること。子供プロフィール(好き嫌い・アレルギー)を登録した上での提案なので、学習機能がなくても一定の的確さは確保できる。

### 本リリースで作る機能

- **調理後フィードバック機能**
  作った料理を子供が「食べた/残した」を記録し、次の提案に活かす
  (画面イメージ:フィードバック入力画面、食べた/残したボタン)

- **データ可視化機能**
  子供の好き嫌いランキングや料理傾向をグラフで表示
  (画面イメージ:ダッシュボード画面、Chart.jsによるグラフ表示)

- **レシピ保存機能**
  AIが提案したレシピをお気に入り登録し、「前作った料理をもう一度作りたい」というニーズに応える
  (画面イメージ:レシピ詳細画面に「お気に入り」ボタン、マイレシピ一覧画面)

## 8. このアプリの懸念点とその対策

### 懸念点①(最優先):食材入力が面倒で継続利用されない可能性

- **何が問題になりそうか**:毎回食材を手入力するのが手間になり、そのうち使われなくなる
- **なぜそう思うか**:「休日の朝、忙しい中でアプリを開いて入力する」というハードル自体が、そもそも面倒に感じられる可能性がある
- **なぜ最優先か**:入力の手間が大きいと、そもそもアプリを開いてもらえず、他の機能が全く使われなくなるため
- **対策(MVP段階)**:よく使う食材をワンタップで選べるようにする
- **対策(本リリース)**:入力候補をサジェスト表示するなど、入力の手間を最小限にするUI設計を心がける

### 懸念点②:AIの提案が実際の味や子供の好みに合わない可能性

- **何が問題になりそうか**:AIが提案したレシピが、実際に作ってみると子供の好みに合わない、味が微妙などのケースが起こりうる
- **なぜそう思うか**:AIはテキスト情報から提案するため、実際の味の再現性や家庭ごとの細かい好みまでは完全に反映しきれない
- **対策(MVP段階)**:NGな食材・調理法を事前に登録できるようにする
- **対策(本リリース)**:調理後フィードバック機能で「食べた/残した」を記録し、繰り返し使うことで提案精度を上げていく

### 懸念点③:OpenAI APIのコストがかさむ可能性

- **何が問題になりそうか**:利用者・利用回数が増えるとAPIコストが増加し、個人開発のままでは運用が難しくなる
- **なぜそう思うか**:GPT-4o-miniは比較的安価とはいえ、リクエスト数に応じて課金されるため、利用が広がるほどコストは積み上がる
- **対策(MVP段階)**:自分と家族のみの利用に絞り、コストを最小限に抑える
- **対策(本リリース)**:キャッシュ機能や利用回数制限などでコストをコントロールする

## 10. 技術スタック(手段としての技術)

### 10-1. 使用予定の技術

- フレームワーク:Django
- DB:PostgreSQL
- デプロイ先:Render
- 使用予定ライブラリ:Chart.js、OpenAI API(GPT-4o-mini)

### 10-2. 技術選定の比較検討

| 種類 | 候補 | 採用/不採用 | 理由 |
|---|---|---|---|
| フレームワーク | Django | 採用 | RUNTEQのPython×AIコースで学習済み。認証・管理画面・ORMが標準搭載で開発が早い |
| フレームワーク | Flask | 不採用 | 軽量だが、認証やDB周りを自分で組む必要があり、卒業制作の期間内では開発コストが高い |
| フレームワーク | FastAPI | 不採用 | API開発に強いが、画面(テンプレート)込みのWebアプリとしてはDjangoの方が完成させやすい |
| DB | PostgreSQL | 採用 | Djangoとの親和性が高く、RenderでもDBとして標準サポートされているため導入しやすい |
| DB | SQLite | 不採用 | 開発初期は手軽だが、本番運用や同時アクセスを考えるとPostgreSQLの方が安定する |
| デプロイ先 | Render | 採用 | RUNTEQでの学習実績があり、DjangoアプリとPostgreSQLを一体でデプロイしやすい |
| デプロイ先 | Heroku | 不採用 | 無料枠の縮小により、個人の卒業制作用途ではRenderの方がコスト面で現実的 |
| AIライブラリ | OpenAI API(GPT-4o-mini) | 採用 | 高精度なレシピ提案が可能で、コストも比較的安価。RUNTEQで学習済み |
| AIライブラリ | Hugging Face Transformers | 不採用 | 自前でモデルを動かす場合、計算リソースやチューニングの手間がかかる |

- 今回チャレンジしたい点:OpenAI APIとの連携部分(食材からのレシピ生成、フィードバックを踏まえた提案精度の向上)をしっかり作り込みたい
- 不安な点:AIのレスポンス速度やAPIコストの管理

### 10-3. 今後の技術的な拡張性

現時点ではDjangoのテンプレートエンジンで完結する構成を想定しており、React等のフロントエンドフレームワーク導入は検討していない。

今後、以下のような状況になった場合にReact等の導入を検討する可能性がある:
- ユーザーからのフィードバックで「画面の動きが遅い」という声が多い場合
- リアルタイムでのデータ更新が必要になった場合
- モバイルアプリ化を検討する場合

休日、妻から「食事作りが当たり前に妻の役割になっている」という指摘を受けたことをきっかけに開発を決めました。休日くらいは自分が食事を担当したいと思う一方、料理経験が少なく献立のアイデアが浮かばず、結局妻に頼ってしまう、という課題を解決するために作りました。

想定ユーザーは、30代〜40代の共働き家庭の夫。子供は小学生〜高校生を想定しています(例:11歳の娘と7歳の息子)。

主な機能は、家にある食材を入力すると子供向け・時短などの条件を反映したレシピをAIが提案する「AIレシピ提案機能」と、子供ごとの好き嫌い・アレルギーを登録できる「子供プロフィール登録機能」です。加えて、調理後に子供の反応(食べた/残した)を記録することで提案精度を上げていく「調理後フィードバック機能」、好き嫌いや料理傾向を可視化する「データ可視化機能」、気に入ったレシピを保存できる「レシピ保存機能」を備えています。

単なるレシピ検索ではなく、子供の反応を学習しながら提案精度が上がっていく点が既存サービスとの違いです。使うほど「わが家仕様」に育っていく、家族のためのAI献立アシスタントを目指しています。

### MVPで実装する予定の機能
- 食材入力機能
- AIレシピ提案機能(子供向け・時短などの条件反映)
- 子供プロフィール登録機能(好き嫌い・アレルギー)

### テーブル詳細

#### users(ユーザー情報)
- id : integer / ユーザーID(PK)
- email : string / ログイン用メールアドレス(ユニーク制約)
- encrypted_password : string / 暗号化済みパスワード
- name : string / 表示名

#### children(子供プロフィール)
- id : integer / 子供ID(PK)
- user_id : integer / users.id への外部キー
- name : string / 子供の名前
- birth_year : integer / 生まれ年
- allergy : text / アレルギー情報

#### ingredients(食材マスタ)
- id : integer / 食材ID(PK)
- name : string / 食材名
- category : string / カテゴリ(肉・野菜など)

#### child_dislike_ingredients(子供の苦手食材/中間テーブル)
- id : integer / ID(PK)
- child_id : integer / children.id への外部キー
- ingredient_id : integer / ingredients.id への外部キー

#### recipes(AIが提案したレシピ)
- id : integer / レシピID(PK)
- user_id : integer / users.id への外部キー
- title : string / 料理名
- used_ingredients : text / 使用食材(入力内容)
- instructions : text / 調理手順
- condition_tag : string / 子供向け・時短などの条件タグ
- is_favorite : boolean / お気に入り登録フラグ

#### recipe_ingredients(レシピの使用食材/中間テーブル)
- id : integer / ID(PK)
- recipe_id : integer / recipes.id への外部キー
- ingredient_id : integer / ingredients.id への外部キー

#### feedbacks(調理後の子供の反応)
- id : integer / ID(PK)
- recipe_id : integer / recipes.id への外部キー
- child_id : integer / children.id への外部キー
- reaction : string / 食べた/残した
- comment : text / コメント

※ 上記全テーブルに created_at / updated_at(datetime)を共通で保持しています。
